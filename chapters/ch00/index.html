들어가며

AWS 콘솔에서 "보안 그룹에서 인바운드 규칙을 추가하세요", "서브넷이 퍼블릭인지 확인하세요", "TLS 1.2 이상을 사용하세요" 같은 말이 들릴 때 감이 안 잡히는 이유는 AWS를 몰라서가 아닙니다. AWS가 다루는 개념들의 토대인 네트워크 기초를 건너뛰었기 때문입니다.

이 챕터는 AWS를 시작하기 전에 반드시 알아야 할 개념들을 다룹니다. 읽기만 해도 되고, 실습은 없습니다. 개념이 잡히면 이후 챕터의 모든 설정이 "왜 이렇게 하는지"와 함께 이해됩니다.

이 챕터를 마치면

"보안 그룹이 22번 포트를 막았다"는 말이 들립니다. "HTTPS는 TLS 핸드셰이크로 암호화된다"는 말이 이해됩니다. "서브넷이 퍼블릭이냐 프라이빗이냐"의 차이가 보입니다.

OSI 7 Layer

네트워크는 왜 7계층으로 나뉘는가

컴퓨터끼리 데이터를 주고받는 일은 복잡합니다. 케이블을 통해 전기 신호를 보내는 물리적 문제부터, IP 주소로 경로를 찾는 문제, 데이터를 빠짐없이 전달하는 문제, 애플리케이션이 데이터를 해석하는 문제까지 여러 층의 문제가 쌓여 있습니다.

OSI 모델은 이 복잡성을 7개의 층(Layer)으로 나눠 각 층이 자기 역할만 담당하게 만든 설계 원칙입니다. 각 층은 바로 아래 층의 서비스를 사용하고, 바로 위 층에 서비스를 제공합니다.

OSI 7계층과 AWS 서비스 매핑. 보안 그룹은 L4(포트)에서 동작하고, VPC는 L3(IP)에서 동작합니다.

AWS에서 자주 나오는 계층

L4 Transport보안 그룹 인바운드 규칙에서 포트 22, 80, 443 지정

TCP와 UDP — 왜 둘 다 있는가

L4(Transport)에는 TCP와 UDP 두 가지 프로토콜이 있습니다.

DNS

DNS — 이름을 IP로 바꾸는 전화번호부

브라우저에 www.parnas.co.kr을 입력하면 실제로는 52.78.XXX.XXX 같은 IP 주소로 연결됩니다. 사람은 이름을 기억하지만 컴퓨터는 IP 주소로 통신하기 때문입니다. DNS(Domain Name System)는 이 변환을 담당합니다.

DNS 조회 흐름. Route 53이 ③의 권한 DNS 역할을 합니다.

NS이 도메인의 권한 DNS 서버호스팅 영역 생성 시 자동 발급
MX메일 서버 지정이메일 수신 경로

TTL — DNS 전파가 왜 느린가

TTL(Time To Live)은 DNS 응답을 캐시에 얼마나 보관할지 초 단위로 지정하는 값입니다. TTL이 3600이면 1시간 동안 캐시된 값을 씁니다. 도메인을 변경했는데 반영이 안 되는 이유가 이겁니다 — 전 세계 DNS 서버의 캐시가 만료될 때까지 기다려야 합니다.

도메인 이전 작업을 하기 전에 TTL을 300(5분)으로 낮춰두면 변경 반영이 빨라집니다.

캐싱

캐싱 — 왜 빠르고 왜 오래된 데이터가 보이는가

캐싱은 자주 쓰는 데이터를 가까운 곳에 미리 복사해두는 기법입니다. 원본까지 매번 가지 않아도 되니 빠릅니다. 대신 원본이 바뀌어도 캐시가 남아 있으면 오래된 데이터가 보입니다.

자주 겪는 문제

CloudFront에 파일을 새로 올렸는데 브라우저에 이전 파일이 계속 보인다면 캐시 때문입니다. CloudFront Invalidation을 실행하거나, 파일명에 버전을 붙이는 방식(app.v2.js)으로 해결합니다.

암호화 · SSL/TLS

HTTPS가 동작하는 원리

HTTP는 주고받는 내용이 평문입니다. 중간에서 누군가 패킷을 가로채면 그대로 읽힙니다. HTTPS는 TLS(Transport Layer Security)로 암호화한 HTTP입니다.

TLS 핸드셰이크 — 연결이 맺어지는 순서

  1. Client Hello 브라우저가 서버에 연결 요청. 지원하는 암호화 방식 목록을 보냅니다.
  2. Server Hello + 인증서 전송 서버가 암호화 방식을 선택하고 SSL 인증서를 보냅니다. 인증서 안에 서버의 공개키가 있습니다.
  3. 인증서 검증 브라우저가 인증서를 CA(인증 기관)에 확인합니다. 유효하면 계속 진행합니다. 주소창의 자물쇠가 이 단계입니다.
  4. 세션 키 교환 이후 통신에 쓸 대칭키를 서버 공개키로 암호화해 전송합니다. 서버만 복호화할 수 있습니다.
  5. 암호화 통신 시작 이제부터는 공유된 대칭키로 데이터를 암호화·복호화합니다.

SSL과 TLS

SSL은 TLS의 구 버전입니다. SSL 3.0 이후 TLS 1.0 → 1.1 → 1.2 → 1.3으로 발전했습니다. 현재 SSL은 보안 취약점으로 사용하지 않지만, 업계 관습적으로 TLS를 "SSL"이라 부르는 경우가 많습니다. ISMS-P 인증에서 TLS 1.2 미만 차단을 요구하는 것도 이 맥락입니다.

RDBMS vs NoSQL

RDS와 DynamoDB — 선택 기준

AWS에서 데이터베이스를 선택할 때 가장 먼저 마주치는 질문입니다. 정해진 답은 없고, 데이터의 성격과 서비스 요구사항에 따라 다릅니다.

RDBMS (관계형 데이터베이스)

데이터를 표(테이블) 형태로 저장하고, 테이블 간 관계를 정의합니다. SQL로 조회합니다.

특징내용
스키마고정 — 컬럼을 미리 정의해야 함
조인여러 테이블을 연결해 복잡한 조회 가능
트랜잭션ACID 보장 (원자성·일관성·격리성·지속성)
확장 방식수직 확장 (서버 사양 업그레이드)
AWS 서비스RDS (MySQL, PostgreSQL, Oracle...)
적합한 경우주문·결제·회원 등 정형 데이터, 복잡한 조인이 필요한 경우

NoSQL (비관계형 데이터베이스)

테이블 형태에 얽매이지 않고 문서·키-값·그래프 등 다양한 형태로 저장합니다.

특징내용
스키마유연 — 항목마다 다른 필드 가능
조인기본적으로 없음 (애플리케이션 레벨에서 처리)
트랜잭션제한적 (서비스마다 다름)
확장 방식수평 확장 (서버를 여러 대로)
AWS 서비스DynamoDB (키-값 · 문서), ElastiCache (Redis)
적합한 경우세션 저장, 로그, 대용량 단순 조회, 스키마가 자주 바뀌는 경우
파르나스 시스템 기준으로 보면

예약·결제·멤버십처럼 데이터 정합성이 중요하고 복잡한 조인이 필요한 경우 → RDS (Oracle, MySQL). 세션 관리나 캐싱처럼 빠른 읽기·쓰기가 필요한 경우 → ElastiCache (Redis). 이 둘을 상황에 맞게 병행하는 게 실무 패턴입니다.
