개념 01

Amazon EC2란

EC2(Elastic Compute Cloud)는 AWS에서 가상 서버를 빌려주는 서비스입니다. 콘솔에서 클릭 몇 번, 또는 명령어 한 줄이면 수십 초 안에 서버가 생깁니다. 필요 없으면 즉시 삭제하고, 사용한 시간만큼만 냅니다.

이름의 Elastic은 "탄력적"이라는 뜻입니다. 트래픽이 몰리면 사양을 올리고, 새벽처럼 한산할 때는 낮춥니다. 온프레미스 서버는 최대 트래픽 기준으로 사야 했지만, EC2는 지금 필요한 만큼만 씁니다.

EC2가 만들어지는 원리

AWS 데이터센터에는 물리 서버가 수십만 대 있습니다. 하이퍼바이저(Hypervisor)라는 소프트웨어가 이 물리 서버를 여러 개의 독립된 가상 머신으로 나눕니다. AWS는 자체 개발한 Nitro System을 하이퍼바이저로 씁니다.

내가 만든 EC2 인스턴스는 다른 고객의 인스턴스와 같은 물리 서버에 있을 수 있지만, 완전히 격리돼 있어서 서로 접근할 수 없습니다. 마치 아파트 각 호수가 같은 건물에 있지만 서로의 공간에 못 들어가는 것처럼요.

🏨
파르나스 인프라 기준으로 보면
Parnas Rewards, TMS API 같은 Spring Boot 백엔드 서비스를 올리는 가장 기본적인 방법이 EC2입니다. VMC(VMware Cloud)에서 EC2로 마이그레이션하는 것도 결국 가상 서버를 다른 플랫폼으로 옮기는 작업입니다. OS 위에 JDK를 설치하고, jar 파일을 올리고, systemd 서비스로 등록합니다.

현업에서 EC2를 쓰는 패턴

EC2 인스턴스 유형은 t3.medium, m6i.xlarge, c6g.2xlarge 같은 형식입니다. 각 부분이 의미하는 바를 알면 어떤 유형을 선택해야 할지 바로 판단됩니다.

t3.micro로 Spring Boot 실행하면?
메모리 1GB는 Spring Boot 기본 실행도 빡빡합니다. JVM 힙 메모리 기본값이 256MB~512MB인데, 나머지 공간이 OS·기타 프로세스가 씁니다. 학습 목적으로 간단한 API 서버를 띄우는 건 괜찮지만, 실제 서비스에는 최소 t3.medium(4GB)을 권장합니다.

파르나스처럼 HikariCP 커넥션 풀 + Tomcat 스레드풀 + 각종 라이브러리가 올라가는 서비스라면 t3.medium은 기본이고, 트래픽에 따라 t3.large 이상이 필요합니다.
개념 03

T타입 버스트 — CPU 크레딧 이해하기

t3, t4g 같은 T타입 인스턴스는 일반 인스턴스와 CPU 동작 방식이 다릅니다. 평소에는 기준 성능(Baseline)으로 동작하다가, 필요할 때 크레딧을 소모해서 순간적으로 높은 성능(Burst)을 냅니다.

크레딧 적립과 소모

인스턴스기준 CPU 성능시간당 크레딧 적립최대 크레딧
t3.nano5%3 credits72 credits
t3.micro10%6 credits144 credits
t3.small20%12 credits288 credits
t3.medium20%24 credits576 credits
t3.large30%36 credits864 credits

CPU 사용률이 기준(예: t3.micro는 10%)보다 낮으면 크레딧이 쌓이고, 높으면 크레딧을 소모합니다. 크레딧 1개 = 1 vCPU가 1분간 100% 동작할 수 있는 양입니다.

🚨
크레딧이 고갈되면?
t3 인스턴스는 기본적으로 unlimited 모드가 켜져 있습니다. 크레딧이 고갈돼도 성능이 떨어지지 않지만, 초과 크레딧 사용에 대해 추가 요금이 부과됩니다. vCPU당 시간당 $0.05 정도입니다.

t2 인스턴스는 standard 모드가 기본이라 크레딧 고갈 시 기준 성능으로 제한됩니다. 갑자기 서버가 느려지면 CloudWatch에서 CPUCreditBalance를 확인하세요.

언제 T타입을 쓰고 언제 M타입을 쓰나

상황권장이유
개발·스테이징 서버T타입평소 CPU 사용률이 낮고 가끔 빌드할 때만 튀어오름. 크레딧으로 충분
학습용 서버T타입켜놓는 시간이 짧고, 비용 절감 중요
프로덕션 API 서버M타입트래픽이 꾸준하면 크레딧 부족 위험. M타입은 항상 일정 성능 보장
CI/CD 빌드 서버C타입빌드 시 CPU 100% 계속 씀. 컴퓨팅 최적화 필요
DB 서버 (직접 설치)R타입메모리가 클수록 캐시 히트율 높아짐
개념 04

EBS — EC2의 하드 드라이브

EBS(Elastic Block Store)는 EC2에 붙이는 가상 SSD/HDD입니다. EC2 인스턴스를 중지하거나 종료해도 EBS 볼륨의 데이터는 기본적으로 유지됩니다(설정에 따라 다름).

EBS는 EC2와 별도로 존재합니다. 인스턴스를 삭제해도 볼륨은 남을 수 있고, 반대로 볼륨을 다른 인스턴스에 붙일 수도 있습니다. 단, 같은 가용 영역 안에서만 연결 가능합니다.

EBS 볼륨 유형

유형종류IOPS서울 요금권장 용도
gp3범용 SSD기본 3,000 / 최대 16,000$0.08/GB·월대부분의 경우 (권장)
gp2범용 SSD크기에 비례 (100~16,000)$0.10/GB·월레거시. gp3로 마이그레이션 권장
io2프로비저닝 SSD최대 256,000$0.138/GB·월고성능 DB, 지연 시간 민감
st1처리량 최적화 HDD최대 500$0.051/GB·월로그, 빅데이터, 순차 읽기
sc1콜드 HDD최대 250$0.018/GB·월거의 안 쓰는 데이터 아카이브
💡
gp2에서 gp3로 전환하면 비용 절감됩니다
gp2는 GB당 $0.10인데 gp3는 $0.08로 20% 저렴하고 성능도 더 좋습니다. 기존 인스턴스의 gp2 볼륨을 무중단으로 gp3로 전환할 수 있습니다. EC2 → 볼륨 → 볼륨 수정에서 유형을 gp3로 바꾸기만 하면 됩니다.
💰
EBS 볼륨은 인스턴스를 종료해도 남을 수 있습니다
인스턴스 생성 시 루트 볼륨은 "종료 시 삭제" 옵션이 기본으로 켜져 있지만, 나중에 추가한 볼륨은 기본으로 남습니다. EC2 → 볼륨 탭에서 available 상태로 남은 볼륨을 꼭 확인하세요. 사용 안 해도 GB당 $0.08/월로 계속 과금됩니다.

스냅샷 — EBS의 백업

스냅샷은 EBS 볼륨의 특정 시점 백업입니다. S3에 저장되며, 스냅샷으로 새 볼륨을 만들거나, 다른 리전으로 복사할 수 있습니다.

항목내용
저장 위치S3 (내부적으로. 직접 S3 버킷에서 보이지는 않음)
요금$0.05/GB·월 (증분 백업이라 변경된 부분만 추가 저장)
활용다른 AZ에 볼륨 생성, 다른 리전으로 AMI 복사, 인스턴스 교체 전 백업
주의실습 후 스냅샷 삭제 안 하면 계속 과금

AMI — 서버의 전체 이미지

AMI(Amazon Machine Image)는 OS + 설치된 소프트웨어 + 설정의 전체 스냅샷입니다. 인스턴스를 만들 때 쓸 템플릿이기도 하고, 잘 설정된 서버를 AMI로 만들어서 여러 인스턴스를 찍어낼 수도 있습니다.

AMI특징권장 상황
Amazon Linux 2023AWS 최적화 · dnf 패키지 · 최신 보안 패치신규 프로젝트 기본 선택
Amazon Linux 2구버전 · 2025년 6월 지원 종료레거시 호환 필요 시만
Ubuntu 22.04 LTSapt 패키지 · 2027년까지 지원Ubuntu 경험자, Docker 많이 쓸 때
Ubuntu 24.04 LTS최신 Ubuntu · 2029년까지 지원신규 Ubuntu 프로젝트
커스텀 AMI내가 만든 이미지Auto Scaling, 빠른 반복 배포
💡
AMI로 Auto Scaling을 빠르게 만드는 법
Java + Spring Boot가 설치된 서버를 AMI로 만들어두면, Auto Scaling이 새 인스턴스를 추가할 때 Java 설치 과정 없이 바로 앱을 실행할 수 있습니다. 배포 시간이 크게 줄어듭니다. "Baked AMI" 방식이라고 합니다.
개념 05

보안 그룹 — 인스턴스 방화벽

보안 그룹은 EC2 인스턴스 앞에 붙는 가상 방화벽입니다. 인바운드(들어오는 트래픽)와 아웃바운드(나가는 트래픽) 규칙을 각각 설정합니다.

보안 그룹의 핵심 특성 4가지

특성내용실무 의미
Stateful 인바운드를 허용하면 그 연결의 응답(아웃바운드)은 자동 허용 HTTP 80을 열면 응답도 자동으로 나간다. 아웃바운드에 별도 설정 불필요
허용만 가능 Allow 규칙만 있고 Deny 규칙은 없음. 명시적으로 허용 안 한 것은 자동 차단 NACL과 달리 거부 규칙이 없어서 관리가 단순함
소스로 보안 그룹 지정 IP 대신 다른 보안 그룹을 소스로 지정 가능 ALB 보안 그룹을 소스로 지정하면, ALB에서 오는 트래픽만 EC2에 들어올 수 있음. IP가 바뀌어도 자동 추적
다중 적용 인스턴스 하나에 보안 그룹 여러 개 적용 가능 (최대 5개) 공통 규칙은 공유 보안 그룹으로, 서비스별 규칙은 별도 보안 그룹으로 관리

실무 보안 그룹 구성 패턴

3티어 아키텍처(ALB → EC2 → RDS)에서는 보안 그룹을 3개로 나눠서 관리합니다.

🛡 3티어 보안 그룹 구성
SG-ALB (ALB용 보안 그룹)
인바운드: TCP 80 ← 0.0.0.0/0 (HTTP 전체 허용)
인바운드: TCP 443 ← 0.0.0.0/0 (HTTPS 전체 허용)
아웃바운드: 전체 허용
↓
SG-EC2 (EC2 앱 서버용)
인바운드: TCP 8080 ← SG-ALB (ALB에서만 허용)
인바운드: TCP 22 ← 내 IP (SSH, 필요 시)
아웃바운드: 전체 허용
↓
SG-RDS (DB용)
인바운드: TCP 3306 ← SG-EC2 (EC2에서만 허용)
아웃바운드: 전체 허용
🚨
SSH 22번을 0.0.0.0/0으로 열면 안 되는 이유
인터넷에는 24시간 포트 스캐너가 돌아다닙니다. 22번 포트가 열리는 순간 수분 안에 발견되고, 자동화된 무차별 대입 공격이 시작됩니다. auth.log를 보면 분당 수십 번의 로그인 시도가 보입니다.

반드시 내 IP만 허용하거나, SSH를 아예 막고 Session Manager를 쓰세요.

키 페어 — SSH 접속의 열쇠

EC2에 SSH로 접속할 때 비밀번호 대신 공개키/개인키 쌍(키 페어)을 씁니다. AWS가 공개키를 인스턴스에 넣어두고, 나는 개인키(.pem 파일)를 가지고 있습니다. 서로 맞아야 접속됩니다.

🔑
.pem 파일은 생성 시 딱 한 번만 다운로드할 수 있습니다
AWS는 개인키를 저장하지 않습니다. 분실하면 해당 인스턴스에 SSH로 다시 접속할 방법이 없습니다. 인스턴스를 새로 만들어야 합니다.

보관 위치 권장: ~/.ssh/ 폴더. 팀 공유 드라이브에는 절대 올리지 마세요.

키 유형 선택

유형특징권장
RSA (.pem)전통적인 방식. 모든 SSH 클라이언트 지원Windows PuTTY, 구형 클라이언트
ED25519 (.pem)더 짧고 빠른 최신 알고리즘macOS, Linux, 최신 Windows

IP 주소 세 종류

종류특징인스턴스 재시작 시과금
퍼블릭 IP 인터넷에서 접근 가능. VPC 설정에 따라 자동 할당 매번 새 IP로 변경됨 인스턴스 실행 중 무료
프라이빗 IP VPC 내부 통신용. 외부에서 직접 접근 불가 변경되지 않음 (고정) 무료
탄력적 IP (EIP) 고정 퍼블릭 IP. 직접 할당해서 관리 변경되지 않음 (내가 릴리스하기 전까지) 미연결 시 시간당 $0.005 ⚠️
💰
탄력적 IP 과금 주의
2024년 2월부터 연결된 탄력적 IP도 시간당 $0.005 과금됩니다. 월 약 $3.6. 작은 금액이지만 알고 있어야 합니다.

연결 안 된 탄력적 IP는 더 비쌉니다. 인스턴스 종료 시 탄력적 IP를 릴리스하는 걸 잊지 마세요.

ENI — 가상 네트워크 카드

ENI(Elastic Network Interface)는 EC2의 가상 네트워크 카드입니다. 하나의 인스턴스에 여러 ENI를 붙이면 여러 서브넷에 동시에 연결하거나, 여러 IP를 가질 수 있습니다.

실무에서는 장애 시 ENI를 다른 인스턴스로 옮겨서 IP를 유지하는 ENI Failover 패턴에 쓰입니다. 탄력적 IP를 붙여서 고정 IP를 유지할 수도 있습니다.

개념 07

EC2 생명 주기 — 상태별 과금 차이

EC2 인스턴스는 여러 상태를 거칩니다. 어떤 상태에서 어떻게 과금되는지를 정확히 알아야 불필요한 비용을 막을 수 있습니다.

상태의미과금
pending인스턴스 시작 중 (부팅)없음
running정상 실행 중✅ 시간당 과금
stopping중지 중없음
stopped중지됨EBS 요금만 (인스턴스 요금 없음)
shutting-down종료 중없음
terminated종료됨 (삭제)없음 (EBS도 기본 삭제)
⚠️
중지(Stop) vs 종료(Terminate) — 이 차이가 제일 중요합니다
중지(Stop): 인스턴스를 껐지만 삭제는 안 된 상태. 재시작 가능. EBS 볼륨 데이터 유지. EBS 요금은 계속 발생. 학습 후 돌아올 예정이면 중지.

종료(Terminate): 인스턴스 완전 삭제. 기본 설정으로는 EBS 루트 볼륨도 함께 삭제. 재시작 불가. 다시는 안 쓸 거면 종료.

학습 목적으로 만든 인스턴스는 종료하세요. 중지하면 EBS 요금이 계속 나옵니다.

재시작(Reboot) vs 중지-시작(Stop-Start)

구분퍼블릭 IP 변경물리 호스트 변경EBS 데이터
재시작(Reboot)유지유지 (같은 서버)유지
중지 → 시작변경됨 (탄력적 IP 없으면)변경될 수 있음유지

서버 설정을 바꾸고 재시작해야 할 때는 재시작(Reboot)을 씁니다. 인스턴스 유형 변경이나 네트워크 설정 변경 후에는 중지 → 시작이 필요합니다.

실습 01

EC2 인스턴스 생성하기

⏱
지금부터 과금이 시작됩니다
인스턴스 생성 완료 순간부터 시간당 요금이 부과됩니다. t3.micro 기준 서울 리전 시간당 $0.013. 실습 완료 후 반드시 종료(Terminate)하세요.

사전 확인

인스턴스 생성 전 반드시 콘솔 우측 상단의 리전이 아시아 태평양(서울) ap-northeast-2인지 확인하세요. 다른 리전에 만들면 나중에 못 찾습니다.

생성 단계별 안내

  1. EC2 콘솔 진입
    AWS 콘솔 상단 검색창에 EC2 입력 → EC2 클릭 → 좌측 메뉴 인스턴스 → 우측 상단 인스턴스 시작 버튼
  2. 이름 설정
    이름: my-spring-server (나중에 구분하기 쉽도록 용도를 이름에 넣어두세요)
    태그는 자동으로 Name 태그로 추가됩니다.
  3. AMI 선택
    Quick Start → Amazon Linux 탭 → Amazon Linux 2023 AMI 선택
    아키텍처: 64비트(x86) (ARM인 Graviton을 선택하려면 별도 확인 필요)
  4. 인스턴스 유형 선택
    학습용: t3.micro (프리 티어 해당, 메모리 1GB)
    Spring Boot 실행용: t3.medium (메모리 4GB, 권장)
    검색창에 유형명을 직접 입력하면 빠릅니다.
  5. 키 페어 생성
    새 키 페어 생성 클릭
    키 페어 이름: my-aws-key
    키 페어 유형: RSA
    프라이빗 키 파일 형식: .pem (macOS/Linux) 또는 .ppk (PuTTY/Windows)
    키 페어 생성 클릭 → .pem 파일 자동 다운로드
    ⚠️ 다운로드된 파일을 ~/.ssh/ 폴더로 이동시켜 보관하세요.
  6. 네트워크 설정
    보안 그룹 생성 선택
    보안 그룹 이름: sg-my-spring-server
    인바운드 규칙:
      • SSH(22) — 소스: 내 IP (My IP 선택하면 자동으로 현재 IP가 채워짐)
      • HTTP(80) — 소스: 위치 무관(0.0.0.0/0)
      • 사용자 지정 TCP(8080) — 소스: 위치 무관 (나중에 ALB로 제한 예정)

    퍼블릭 IP 자동 할당: 활성화
  7. 스토리지 구성
    기본값: 8 GiB gp3
    학습용으로는 충분합니다. 함부로 크기를 늘리지 마세요 — 줄이는 건 안 됩니다.
    "종료 시 삭제" 옵션이 켜져 있는지 확인 (기본값: 켜짐)
  8. 인스턴스 시작
    우측 요약 패널에서 설정 최종 확인 → 인스턴스 시작
    상태가 pending → running으로 바뀔 때까지 1~2분 대기
💡
인스턴스 목록에서 확인할 정보
인스턴스 선택 → 하단 세부 정보 탭에서:
• 퍼블릭 IPv4 주소 → SSH 접속에 필요
• 프라이빗 IPv4 주소 → VPC 내부 통신에 사용
• 인스턴스 상태 → running이어야 접속 가능
• 가용 영역 → 어느 AZ에 생성됐는지
실습 02

SSH로 EC2 접속하기

인스턴스 상태가 running이 되고 나서 1~2분 정도 더 기다려야 SSH 서버가 완전히 올라옵니다. 너무 빨리 접속하면 Connection refused가 날 수 있습니다.

macOS / Linux

💻 터미널
# 1. 키 파일을 ~/.ssh/ 로 이동 (이미 이동했다면 생략)
mv ~/Downloads/my-aws-key.pem ~/.ssh/

# 2. 키 파일 권한 설정 — 반드시 해야 함. 안 하면 접속 거부됨
chmod 400 ~/.ssh/my-aws-key.pem

# 3. SSH 접속 (퍼블릭 IP는 EC2 콘솔에서 확인)
ssh -i ~/.ssh/my-aws-key.pem ec2-user@퍼블릭IP주소

# 예시
ssh -i ~/.ssh/my-aws-key.pem ec2-user@13.125.xxx.xxx

# 처음 접속 시 "Are you sure you want to continue connecting?" 질문
# yes 입력 후 엔터

Windows (PowerShell)

💻 PowerShell
# Windows 10 이상은 기본 SSH 클라이언트 포함
ssh -i C:\Users\사용자명\.ssh\my-aws-key.pem ec2-user@퍼블릭IP

# Windows에서 chmod 대신 — 키 파일 우클릭 → 속성 → 보안 → 고급
# 상속 비활성화 → 현재 사용자만 남기고 모두 삭제

OS별 기본 사용자 이름

AMI기본 사용자 이름
Amazon Linux 2, Amazon Linux 2023ec2-user
Ubuntuubuntu
Debianadmin
RHELec2-user 또는 root
WindowsAdministrator

SSH 접속 트러블슈팅

에러원인해결
Connection refused SSH 서버 미시작 또는 보안 그룹 22 포트 미개방 1~2분 더 기다리기. 보안 그룹 인바운드 22 포트 확인
Connection timed out 보안 그룹에 내 IP가 없거나 퍼블릭 IP가 없음 보안 그룹 소스 IP 확인 (내 IP가 바뀌었을 수 있음). 퍼블릭 IP 자동 할당 여부 확인
Permission denied (publickey) 키 파일이 틀렸거나 권한 문제 chmod 400 확인. 키 파일 경로 확인. 사용자 이름 확인 (ec2-user vs ubuntu)
WARNING: UNPROTECTED PRIVATE KEY 키 파일 권한이 너무 넓음 chmod 400 ~/.ssh/my-aws-key.pem 실행
접속 됐다가 끊김 SSH keepalive 미설정 ~/.ssh/config에 ServerAliveInterval 60 추가

SSH Config 설정 — 매번 긴 명령어 안 치는 법

📄 ~/.ssh/config
# ~/.ssh/config 파일 생성 또는 편집
Host my-spring-server
    HostName 13.125.xxx.xxx
    User ec2-user
    IdentityFile ~/.ssh/my-aws-key.pem
    ServerAliveInterval 60
    ServerAliveCountMax 3

# 이제 이렇게 접속 가능
ssh my-spring-server
실습 03

Java 설치 및 Spring Boot 배포

1단계 — 시스템 업데이트 및 Java 설치

💻 EC2 터미널 — Amazon Linux 2023
# 시스템 패키지 업데이트
sudo dnf update -y

# Java 17 설치 (Amazon Corretto — AWS 최적화 OpenJDK)
sudo dnf install java-17-amazon-corretto -y

# 설치 확인
java -version
# openjdk version "17.x.x" ...

# 앱 디렉토리 생성
mkdir -p ~/app
cd ~/app

2단계 — jar 파일 업로드

로컬 터미널(EC2가 아닌 내 PC)에서 실행합니다.

💻 로컬 터미널 — scp로 파일 전송
# Gradle 빌드 (로컬에서)
./gradlew bootJar

# scp로 EC2에 업로드
scp -i ~/.ssh/my-aws-key.pem \
  ./build/libs/myapp-0.0.1-SNAPSHOT.jar \
  ec2-user@퍼블릭IP:~/app/app.jar

# SSH Config 설정했으면 더 간단하게
scp ./build/libs/myapp-0.0.1-SNAPSHOT.jar \
  my-spring-server:~/app/app.jar

3단계 — 임시 실행 (테스트용)

💻 EC2 터미널 — 임시 실행
# 임시 실행 (SSH 세션 끊기면 종료됨)
java -jar ~/app/app.jar

# 백그라운드 실행 (SSH 끊겨도 유지, 로그는 app.log로)
nohup java -Xmx512m -jar ~/app/app.jar \
  --spring.profiles.active=prod \
  > ~/app/app.log 2>&1 &

# 실행 확인
curl localhost:8080/health

# 프로세스 확인
ps aux | grep java

# 종료 (PID 확인 후)
kill $(ps aux | grep java | grep -v grep | awk '{print $2}')
💡
-Xmx 메모리 설정
-Xmx512m은 JVM 최대 힙 메모리를 512MB로 제한합니다. t3.micro(1GB)에서는 -Xmx384m, t3.medium(4GB)에서는 -Xmx1g~-Xmx2g 정도가 적당합니다. 설정 안 하면 JVM이 메모리의 25~50%를 가져가는데, t3.micro에서는 OOM이 날 수 있습니다.

4단계 — systemd 서비스 등록 (운영용)

nohup은 임시방편입니다. 서버가 재시작되면 앱도 꺼집니다. systemd에 등록하면 서버 재시작 시 자동으로 앱이 뜹니다.

💻 EC2 터미널 — systemd 서비스 등록
# 서비스 파일 생성
sudo tee /etc/systemd/system/myapp.service << 'EOF'
[Unit]
Description=My Spring Boot Application
After=network.target
Wants=network-online.target

[Service]
Type=simple
User=ec2-user
WorkingDirectory=/home/ec2-user/app
ExecStart=/usr/bin/java -Xmx1g -jar /home/ec2-user/app/app.jar \
    --spring.profiles.active=prod
ExecStop=/bin/kill -SIGTERM $MAINPID
Restart=on-failure
RestartSec=10
StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapp

# 환경변수 — 민감한 값은 여기에 (코드에 하드코딩 금지)
Environment="DB_HOST=your-rds-endpoint.ap-northeast-2.rds.amazonaws.com"
Environment="DB_NAME=mydb"
Environment="DB_USER=admin"
Environment="DB_PASS=yourpassword"

[Install]
WantedBy=multi-user.target
EOF

# systemd 재로드 및 서비스 활성화
sudo systemctl daemon-reload
sudo systemctl enable myapp    # 부팅 시 자동 시작
sudo systemctl start myapp     # 지금 바로 시작

# 상태 확인
sudo systemctl status myapp

# 실시간 로그 확인
sudo journalctl -u myapp -f

# 앱 재시작 (코드 배포 후)
sudo systemctl restart myapp

5단계 — 브라우저에서 접속 확인

브라우저에서 http://퍼블릭IP:8080/health로 접속해서 응답이 오면 성공입니다.

접속이 안 되면 보안 그룹 인바운드에 TCP 8080이 열려 있는지 확인하세요.

실습 04

유저 데이터 — 인스턴스 첫 부팅 시 자동 실행

인스턴스 생성 시 유저 데이터(User Data)에 스크립트를 넣으면, 인스턴스가 처음 부팅할 때 root 권한으로 자동 실행됩니다. Java 설치, S3에서 jar 다운로드, 서비스 등록까지 자동화할 수 있습니다.

📄 유저 데이터 스크립트 예시
#!/bin/bash
# 이 스크립트는 인스턴스 최초 부팅 시 root로 실행됩니다
set -e  # 에러 시 중단

# 시스템 업데이트
dnf update -y

# Java 설치
dnf install java-17-amazon-corretto -y

# 앱 디렉토리 생성
mkdir -p /home/ec2-user/app
chown ec2-user:ec2-user /home/ec2-user/app

# S3에서 jar 다운로드 (IAM 역할이 있어야 함)
aws s3 cp s3://my-deploy-bucket/app.jar /home/ec2-user/app/app.jar

# systemd 서비스 파일 생성
cat > /etc/systemd/system/myapp.service << 'SERVICEEOF'
[Unit]
Description=My Spring Boot Application
After=network.target

[Service]
Type=simple
User=ec2-user
WorkingDirectory=/home/ec2-user/app
ExecStart=/usr/bin/java -Xmx1g -jar /home/ec2-user/app/app.jar
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
SERVICEEOF

# 서비스 시작
systemctl daemon-reload
systemctl enable myapp
systemctl start myapp

EC2 생성 화면 → 고급 세부 정보 섹션 → 맨 아래 사용자 데이터 칸에 위 스크립트를 붙여넣으면 됩니다.

💡
유저 데이터 실행 로그 확인
유저 데이터 스크립트가 제대로 실행됐는지 확인하려면:
sudo cat /var/log/cloud-init-output.log
에러가 있으면 여기서 확인할 수 있습니다.

메타데이터 — 인스턴스 자기 자신 정보 조회

EC2 인스턴스 안에서 자기 자신의 인스턴스 ID, IP, 리전 등을 조회하려면 메타데이터 서버(169.254.169.254)를 씁니다.

💻 메타데이터 조회
# IMDSv2 방식 (보안 강화 버전 — 권장)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# 인스턴스 ID
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id
# i-0a1b2c3d4e5f67890

# 퍼블릭 IP
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4
# 13.125.xxx.xxx

# 리전
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/region
# ap-northeast-2

# 인스턴스 유형
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-type
# t3.medium
실습 05

탄력적 IP 할당하기

인스턴스를 중지했다가 다시 시작하면 퍼블릭 IP가 바뀝니다. DNS에 등록하거나 팀원에게 주소를 알려줄 때 문제가 됩니다. 탄력적 IP를 붙이면 고정됩니다.

  1. 탄력적 IP 할당
    EC2 콘솔 → 좌측 메뉴 탄력적 IP → 탄력적 IP 주소 할당
    네트워크 경계 그룹: ap-northeast-2 그대로
    할당 클릭
  2. 인스턴스에 연결
    할당된 IP 선택 → 작업 → 탄력적 IP 주소 연결
    인스턴스: 연결할 EC2 선택
    프라이빗 IP: 자동 선택
    연결
  3. 확인
    인스턴스 목록에서 해당 인스턴스 선택 → 퍼블릭 IPv4가 탄력적 IP로 변경됐는지 확인
💰
실습 후 반드시 릴리스
인스턴스를 종료하면 탄력적 IP 연결이 끊어지고, 연결 안 된 탄력적 IP는 시간당 $0.005 과금됩니다. 실습 후 반드시:
탄력적 IP 선택 → 작업 → 탄력적 IP 주소 릴리스
실습 06

EC2에 IAM 역할 부여하기

EC2에서 S3, SSM, CloudWatch 등 다른 AWS 서비스에 접근하려면 IAM 역할이 필요합니다. 액세스 키를 코드에 박는 방식 대신, 인스턴스에 역할을 붙이면 SDK가 자동으로 임시 자격증명을 가져옵니다.

IAM 역할 생성

  1. IAM 콘솔 → 역할 → 역할 생성
    신뢰할 수 있는 엔티티 유형: AWS 서비스
    사용 사례: EC2
    다음
  2. 권한 정책 추가
    학습용으로 아래 정책들을 추가합니다:
    • AmazonS3FullAccess — S3 파일 업로드/다운로드
    • AmazonSSMManagedInstanceCore — Session Manager 접속
    • CloudWatchAgentServerPolicy — CloudWatch 지표 수집
    실무에서는 최소 권한 원칙에 따라 필요한 것만 부여합니다.
  3. 역할 이름 지정 및 생성
    역할 이름: ec2-app-role
    역할 생성

EC2에 IAM 역할 연결

  1. EC2 콘솔 → 인스턴스 선택 → 작업 → 보안 → IAM 역할 수정
  2. IAM 역할: ec2-app-role 선택 → IAM 역할 업데이트

역할 동작 확인

💻 EC2 터미널 — IAM 역할 확인
# AWS CLI로 현재 자격증명 확인
aws sts get-caller-identity
# {
#   "UserId": "AROA...",
#   "Account": "325355907088",
#   "Arn": "arn:aws:sts::325355907088:assumed-role/ec2-app-role/i-xxx"
# }

# S3 버킷 목록 조회 (S3 접근 권한 확인)
aws s3 ls

# 특정 버킷에 파일 업로드 테스트
echo "test" > /tmp/test.txt
aws s3 cp /tmp/test.txt s3://my-bucket/test.txt
실습 07

EC2 접속 방법 3가지

방법키 페어 필요포트 22 필요기록 남음권장 상황
SSH✅✅❌ (별도 설정 필요)일반적인 접속
EC2 Instance Connect❌✅ (EC2IC 포트)CloudTrail키 파일 없을 때 빠른 접속
Session Manager❌❌CloudTrail + 세션 로그보안 강화 환경, ISMS-P 대응

EC2 Instance Connect 사용법

  1. EC2 콘솔 → 인스턴스 선택 → 연결
  2. EC2 Instance Connect 탭 선택
  3. 사용자 이름: ec2-user 확인
  4. 연결 클릭 → 브라우저에서 터미널 열림
⚠️
EC2 Instance Connect도 보안 그룹에 특정 CIDR 허용 필요
EC2 Instance Connect는 AWS가 관리하는 IP 범위에서 SSH 연결을 합니다. 보안 그룹에서 해당 리전의 EC2 Instance Connect IP를 허용해야 합니다. 서울 리전 기준: 13.209.1.56/29

또는 보안 그룹에서 SSH 소스를 AWS 서비스 com.amazonaws.ap-northeast-2.ec2-instance-connect로 지정할 수 있습니다.

Session Manager 설정 (권장)

Session Manager는 SSH 포트(22)를 완전히 닫아도 EC2에 접속할 수 있습니다. IAM 권한으로 제어하고, 모든 세션이 CloudTrail에 기록됩니다. ISMS-P 접근 이력 감사에 매우 유리합니다.

  1. IAM 역할에 SSM 정책 추가
    IAM → 역할 → ec2-app-role → 정책 연결
    AmazonSSMManagedInstanceCore 추가
  2. SSM Agent 확인
    Amazon Linux 2023에는 SSM Agent가 기본 설치돼 있습니다.
    sudo systemctl status amazon-ssm-agent로 확인
  3. 접속
    EC2 콘솔 → 인스턴스 선택 → 연결 → Session Manager → 연결
    또는 AWS CLI: aws ssm start-session --target i-인스턴스ID
💻 Session Manager CLI 접속
# Session Manager Plugin 설치 필요 (로컬 PC)
# macOS: brew install --cask session-manager-plugin

# 접속
aws ssm start-session --target i-0a1b2c3d4e5f67890

# SSH 터널링도 가능 (포트 포워딩)
aws ssm start-session \
  --target i-0a1b2c3d4e5f67890 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["8080"],"localPortNumber":["8080"]}'
# 이제 localhost:8080으로 EC2 앱에 접속 가능
실습 08

인스턴스 사이즈 변경하기

서비스가 성장해서 t3.medium으로 부족해지면 t3.large로 업그레이드할 수 있습니다. 반대도 가능합니다. 단, 인스턴스를 중지한 상태에서만 가능합니다.

  1. 인스턴스 중지
    인스턴스 선택 → 인스턴스 상태 → 중지
    상태가 stopped로 바뀔 때까지 대기 (1~2분)
  2. 인스턴스 유형 변경
    인스턴스 선택 → 작업 → 인스턴스 설정 → 인스턴스 유형 변경
    원하는 유형 선택 → 적용
  3. 인스턴스 시작
    인스턴스 선택 → 인스턴스 상태 → 시작
    ⚠️ 탄력적 IP 없으면 퍼블릭 IP가 변경됩니다.
💡
같은 패밀리 내에서만 즉시 변경 가능합니다
t3.micro → t3.medium: 가능
t3.medium → m6i.large: 가능 (다른 패밀리도 가능)
x86 → Graviton(ARM): 앱이 ARM 컴파일돼야 함. 함부로 바꾸면 앱이 안 뜰 수 있음
트러블슈팅 & 정리

자주 겪는 문제와 해결법

증상원인해결
인스턴스 목록에 서버가 없음 리전이 다름 콘솔 우측 상단 리전을 서울(ap-northeast-2)로 변경
SSH Connection timed out 보안 그룹 22 포트 미개방 or 내 IP 변경 보안 그룹 인바운드 확인. "내 IP"를 다시 설정
Permission denied (publickey) 키 파일 불일치 or 권한 문제 chmod 400 확인. 키 파일 경로 확인. 사용자 이름 확인
Spring Boot 접속 안 됨 앱 미실행 or 포트 미개방 journalctl -u myapp 확인. 보안 그룹 8080 확인
서버가 갑자기 느려짐 T타입 CPU 크레딧 소진 CloudWatch CPUCreditBalance 확인. 인스턴스 유형 업그레이드 고려
Out of memory / OOM Killer JVM 힙 메모리 과다 사용 -Xmx 설정 확인. free -h로 메모리 현황 확인. 인스턴스 사이즈 업그레이드
재시작 후 앱이 안 뜸 systemd 미등록 systemctl enable myapp 확인. systemctl status myapp으로 에러 확인

유용한 진단 명령어

💻 EC2 상태 진단 명령어 모음
# 메모리 현황
free -h

# CPU 사용률 실시간
top
# 또는
htop  # sudo dnf install htop -y 로 설치

# 디스크 사용량
df -h

# 네트워크 연결 상태
ss -tlnp  # 어떤 포트가 열려 있는지

# Java 프로세스 확인
ps aux | grep java
jps -l  # JVM 프로세스만 보기

# 앱 로그 (systemd 서비스인 경우)
sudo journalctl -u myapp -f          # 실시간
sudo journalctl -u myapp --since today  # 오늘 로그
sudo journalctl -u myapp -n 100      # 최근 100줄

# 시스템 로그
sudo tail -f /var/log/messages
sudo tail -f /var/log/cloud-init-output.log  # 유저 데이터 실행 로그

# 특정 포트 접속 테스트
curl -v localhost:8080/health
nc -zv localhost 8080

실습 후 정리 체크리스트

🗑
아래 순서대로 정리하세요 — 빠뜨리면 계속 과금됩니다
  1. 인스턴스 선택 → 인스턴스 상태 → 종료(Terminate)
    ⚠️ 중지(Stop)가 아닌 종료(Terminate)!
  2. EC2 → 볼륨 탭 → available 상태 볼륨 선택 → 삭제
  3. EC2 → 탄력적 IP → 연결 안 된 IP → 작업 → 릴리스
  4. EC2 → 스냅샷 → 학습 중 만든 스냅샷 삭제
  5. EC2 → AMI → 학습 중 만든 AMI → 등록 취소
  6. EC2 → 보안 그룹 → 학습용 보안 그룹 삭제 (기본 보안 그룹은 삭제 불가)
  7. EC2 → 키 페어 → 학습용 키 페어 삭제 (로컬 .pem 파일도 삭제)
📌 CH02 핵심 개념 요약
인스턴스 유형 패밀리(t=버스트·m=균형·c=컴퓨팅·r=메모리) + 세대(숫자 높을수록 최신) + 크기. Spring Boot 최소 t3.medium 권장
T타입 버스트 기준 성능 이하면 크레딧 적립, 이상이면 소모. t3는 unlimited 모드 기본 — 고갈돼도 동작하지만 추가 과금
EBS 가상 디스크. gp3 권장($0.08/GB). 인스턴스 종료 후 available 볼륨 잔류 주의
보안 그룹 Stateful 방화벽. SSH 22 소스는 내 IP만. 앱 포트는 ALB 보안 그룹을 소스로
탄력적 IP 고정 퍼블릭 IP. 연결 상태여도 시간당 $0.005 과금. 미연결 시 더 비쌈. 실습 후 릴리스 필수
중지 vs 종료 중지 = EBS 요금 계속. 종료 = 완전 삭제. 학습 후엔 종료
IAM 역할 EC2에 붙이면 임시 자격증명 자동 발급. 액세스 키 코드 삽입 금지
Session Manager SSH 포트 없이 IAM 권한으로 접속. 모든 세션 CloudTrail 기록. ISMS-P 대응에 유리
systemd Spring Boot를 서비스로 등록하면 서버 재시작 시 자동 실행. journalctl로 로그 확인
