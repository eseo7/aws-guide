CHAPTER 03

Amazon VPC

가상 네트워크 설계

핵심 서비스 NAT 과금

VPC는 AWS 위에 나만의 가상 데이터센터를 만드는 서비스입니다. EC2, RDS 등 모든 리소스는 VPC 안에서 동작합니다. 네트워크 구조를 직접 설계하고 인터넷 연결과 보안을 제어할 수 있습니다.

01

VPC란 무엇인가

물리적인 데이터센터에는 서버실이 있고, 내부 네트워크와 외부 인터넷을 분리합니다. AWS에서는 이 역할을 VPC(Virtual Private Cloud)가 합니다.

VPC는 AWS 계정 안에서 논리적으로 격리된 가상 네트워크 공간입니다. VPC를 만들면 IP 주소 범위(CIDR)를 직접 정하고, 그 안에서 서브넷·라우팅·보안을 모두 직접 제어할 수 있습니다.

💡
기본 VPC(Default VPC)
AWS 계정을 만들면 각 리전에 기본 VPC가 자동 생성됩니다. CIDR은 172.31.0.0/16이며 모든 서브넷이 퍼블릭으로 설정됩니다. 빠른 테스트에는 편리하지만, 실제 서비스에서는 직접 설계한 커스텀 VPC 사용을 권장합니다.

CIDR 블록

VPC 생성 시 IP 주소 범위를 CIDR 표기법으로 지정합니다. 10.0.0.0/16은 10.0.0.0 ~ 10.0.255.255 범위로 총 65,536개 IP 주소를 의미합니다.

CIDR IP 범위 사용 가능 IP 수 용도
10.0.0.0/8 10.0.0.0 ~ 10.255.255.255 약 1,677만 대규모 기업
10.0.0.0/16 10.0.0.0 ~ 10.0.255.255 65,536 일반 서비스 (권장)
10.0.0.0/24 10.0.0.0 ~ 10.0.0.255 256 소규모 서브넷
⚠️
AWS가 예약하는 IP 5개
각 서브넷에서 첫 4개(네트워크 주소·라우터·DNS·예약)와 마지막 1개(브로드캐스트)는 AWS가 예약합니다. /24 서브넷(256개)이라면 실제 사용 가능한 IP는 251개입니다.
02

서브넷 — 퍼블릭과 프라이빗

VPC는 하나의 큰 네트워크 공간입니다. 이 공간을 용도별로 나눈 것이 서브넷(Subnet)입니다. 서브넷은 반드시 하나의 가용 영역(AZ)에 속합니다.

퍼블릭 서브넷
  • 인터넷 게이트웨이(IGW)로 라우팅됨
  • 퍼블릭 IP 할당 가능
  • 외부에서 직접 접근 가능
  • 웹 서버, Load Balancer, Bastion Host 배치
프라이빗 서브넷
  • IGW로 직접 라우팅 없음
  • 퍼블릭 IP 없음
  • 외부에서 직접 접근 불가
  • DB 서버, 앱 서버, 내부 API 배치

고가용성을 위한 멀티 AZ 구성

실제 서비스에서는 한 AZ에 장애가 생겨도 서비스가 계속되도록 여러 AZ에 서브넷을 분산합니다. 아래는 전형적인 2-AZ 구성입니다.

서브넷 AZ-a (ap-northeast-2a) AZ-b (ap-northeast-2b)
퍼블릭 10.0.1.0/24 10.0.3.0/24
프라이빗 10.0.2.0/24 10.0.4.0/24
03

인터넷 게이트웨이 (IGW)

인터넷 게이트웨이(IGW)는 VPC와 인터넷을 연결하는 관문입니다. VPC 하나에 IGW 하나를 연결하며, IGW 자체는 고가용성이 보장되어 별도 이중화 설정이 필요 없습니다.

IGW 연결 절차

  1. IGW 생성
  2. VPC에 IGW Attach (연결)
  3. 퍼블릭 서브넷의 라우팅 테이블에 0.0.0.0/0 → IGW 추가
  4. EC2에 퍼블릭 IP 또는 탄력적 IP(EIP) 할당
💡
서브넷 자체가 퍼블릭이 되는 조건
서브넷이 "퍼블릭"으로 불리려면 두 조건이 모두 충족되어야 합니다. ① 라우팅 테이블에 0.0.0.0/0 → IGW 규칙 존재, ② EC2에 퍼블릭 IP(또는 EIP) 할당. 둘 중 하나라도 없으면 인터넷에서 접근 불가합니다.
04

라우팅 테이블

라우팅 테이블(Route Table)은 네트워크 트래픽을 어디로 보낼지 결정하는 규칙 목록입니다. 모든 서브넷은 반드시 하나의 라우팅 테이블과 연결됩니다.

퍼블릭 서브넷 라우팅 테이블

목적지 (Destination) 대상 (Target) 설명
10.0.0.0/16 local VPC 내부 통신 (자동 생성, 삭제 불가)
0.0.0.0/0 igw-xxxxxxxx 인터넷 트래픽 → IGW로

프라이빗 서브넷 라우팅 테이블

목적지 (Destination) 대상 (Target) 설명
10.0.0.0/16 local VPC 내부 통신 (자동 생성)
0.0.0.0/0 nat-xxxxxxxx 외부 통신 → NAT 게이트웨이로
💡
라우팅 우선순위 — 더 구체적인 경로가 우선
10.0.0.0/16과 0.0.0.0/0이 모두 있을 때, VPC 내부 IP(10.0.x.x)는 local로, 그 외 모든 트래픽은 IGW나 NAT로 라우팅됩니다. prefix가 길수록(더 구체적일수록) 우선순위가 높습니다.
05

NAT 게이트웨이

프라이빗 서브넷의 EC2는 외부에서 직접 접근할 수 없습니다. 하지만 소프트웨어 업데이트나 외부 API 호출처럼 EC2가 인터넷에 나가야 하는 경우가 있습니다. 이때 NAT 게이트웨이를 사용합니다.

NAT 게이트웨이는 반드시 퍼블릭 서브넷에 위치하며, 탄력적 IP(EIP)가 필요합니다.

권장 상황 프로덕션 비용 최소화 테스트
06

보안 그룹 vs NACL

VPC에는 두 가지 방화벽이 있습니다. 보안 그룹(Security Group)은 EC2 인스턴스 수준, NACL(Network ACL)은 서브넷 수준에서 동작합니다.

보안 그룹 (Security Group)
  • EC2 인스턴스에 적용
  • Stateful — 인바운드 허용 시 아웃바운드 자동 허용
  • 허용(Allow) 규칙만 설정 가능
  • 여러 EC2에 동일 그룹 적용 가능
  • EC2 간 보안 그룹 참조 가능
NACL (Network ACL)
  • 서브넷 전체에 적용
  • Stateless — 인바운드·아웃바운드 각각 설정 필요
  • 허용(Allow) + 거부(Deny) 규칙 모두 설정
  • 규칙 번호 순서대로 처리 (낮을수록 우선)
  • 특정 IP 차단에 효과적

Stateful vs Stateless 이해하기

보안 그룹 (Stateful)
클라이언트가 EC2에 HTTP 요청(인바운드 80포트)을 보낼 때, 인바운드를 허용하면 EC2의 응답(아웃바운드)은 자동으로 허용됩니다. "대화의 상태를 기억"합니다.
NACL (Stateless)
각 패킷을 독립적으로 평가합니다. 인바운드 80포트를 허용해도, EC2 응답의 아웃바운드(임시 포트 1024~65535)도 별도 허용 규칙을 추가해야 합니다.

보안 그룹 인바운드 규칙 예시

유형 프로토콜 포트 소스 설명
HTTP TCP 80 0.0.0.0/0 전체 인터넷 HTTP 허용
HTTPS TCP 443 0.0.0.0/0 전체 인터넷 HTTPS 허용
SSH TCP 22 내 IP/32 관리자 IP만 SSH 허용
MySQL/Aurora TCP 3306 앱서버 보안그룹 ID 앱 서버에서만 DB 접근
07

Bastion Host

프라이빗 서브넷의 EC2는 퍼블릭 IP가 없어 외부에서 SSH로 직접 접속할 수 없습니다. Bastion Host(점프 서버)는 퍼블릭 서브넷에 위치한 EC2로, 관리자가 이 서버를 경유해 프라이빗 EC2에 접속합니다.

관리자
(로컬 PC)
→ SSH →
🏰
Bastion Host
(퍼블릭 서브넷)
→ SSH →
🖥️
프라이빗 EC2
(프라이빗 서브넷)

Bastion Host 보안 설정

Bastion Host 보안 그룹
  • 인바운드: SSH(22) — 관리자 IP만
  • 아웃바운드: SSH(22) — 프라이빗 서브넷 CIDR
프라이빗 EC2 보안 그룹
  • 인바운드: SSH(22) — Bastion SG ID 참조
  • 아웃바운드: 필요한 포트만 허용
💡
더 안전한 대안 — AWS Systems Manager Session Manager
SSH 포트(22)를 열지 않아도 브라우저 또는 AWS CLI로 프라이빗 EC2에 접속할 수 있습니다. IAM으로 접근을 제어하고, 세션 로그를 CloudTrail에 기록해 감사(Audit)가 가능합니다. 신규 아키텍처에서는 Bastion Host 대신 Session Manager 사용을 권장합니다.
08

VPC Peering

두 VPC 사이를 AWS 내부 프라이빗 네트워크로 연결하는 기능입니다. 같은 계정·다른 계정, 같은 리전·다른 리전 간 모두 연결 가능합니다.

⚠️
VPC Peering 핵심 제약사항
① CIDR 겹침 불가 — 두 VPC의 IP 범위가 겹치면 연결 불가. 미리 CIDR 계획 필수.
② 전이(Transitive) 라우팅 불가 — A↔B, B↔C가 연결되어도 A↔C 통신 안 됨. A↔C 별도 Peering 필요.
③ 연결 후 양쪽 라우팅 테이블에 각각 경로를 추가해야 통신 가능.

여러 VPC 연결 — Transit Gateway

VPC가 많아지면 Peering 수가 폭발적으로 늘어납니다(n개 VPC → n×(n-1)/2개 Peering). 이때는 Transit Gateway를 허브로 두고 각 VPC를 스포크처럼 연결합니다. 전이 라우팅을 지원하며 관리가 훨씬 단순해집니다.

09

전형적인 3-Tier 아키텍처

실제 서비스에서 자주 사용하는 구성입니다. 웹·앱·DB 계층을 각각 다른 서브넷에 배치해 보안과 가용성을 높입니다.

계층 서브넷 배치 리소스 인터넷 접근
웹 계층 퍼블릭 ALB (Application Load Balancer) 허용 (외부 요청 수신)
앱 계층 프라이빗 EC2 (웹·API 서버) 차단 (NAT로 아웃바운드만)
DB 계층 프라이빗 RDS (MySQL, PostgreSQL 등) 차단 (VPC 내부만)

핵심 정리

VPC
AWS 위의 가상 데이터센터. CIDR 블록으로 IP 범위 지정. 계정당 리전별 기본 VPC 1개 자동 생성.
서브넷
VPC를 나눈 단위. 퍼블릭(IGW 연결)과 프라이빗(IGW 없음). 단일 AZ에 속함.
IGW
VPC ↔ 인터넷 연결 관문. VPC당 1개. 고가용성 자동 보장. 과금 없음.
라우팅 테이블
트래픽 목적지 결정 규칙. 더 구체적인 경로(긴 prefix)가 우선.
NAT 게이트웨이
프라이빗 EC2의 아웃바운드 인터넷 통신. 퍼블릭 서브넷에 위치. 시간당 과금 주의.
보안 그룹
인스턴스 수준 방화벽. Stateful. 허용 규칙만. EC2 간 SG 참조 가능.
NACL
서브넷 수준 방화벽. Stateless. 허용·거부 규칙 모두. 규칙 번호 순 처리.
Bastion Host
프라이빗 EC2 접속 경유 서버. Session Manager로 대체 권장.
VPC Peering
VPC 간 프라이빗 연결. CIDR 겹침 불가. 전이 라우팅 불가. 다수 VPC는 Transit Gateway 사용.
